# Requirements

For durable sources or records, use [project-knowledge](../project-knowledge/SKILL.md).
Keep facts, assumptions, proposals, confirmed decisions, and implementation authority
distinct. Existing authorization persists; these rules add no approval stages.

Describe outcomes and consequential boundaries in the project's language. Derive
acceptance examples from intended behavior, including relevant initial conditions,
actions, results, and failure boundaries. Investigate accessible facts yourself;
ask about unresolved consequential choices. Do not infer expectations from code or
fill a template with invented decisions. Implementation may precede tests.

Update agreed documentation routinely. Use [to-spec](../to-spec/SKILL.md) for synthesis
and [to-tickets](../to-tickets/SKILL.md) when decomposition helps. An intensive interview
is optional, not a prerequisite for every requirement.

Record substantive bugs and fixes regardless of patch size. Update the matching item;
create a separate finding for a distinct issue. Capture expected versus observed behavior,
reproduction, known cause, and fix evidence. Preserve a useful lesson when there is one.
An editorial typo needs no record; a misspelled configuration key changing behavior does.
Discovery does not authorize unrelated fixes.

When intent changes, reassess affected acceptance examples, decisions, and evidence.
Link verification to its requirement and checked state; distinguish supported, failed,
and missing or stale evidence. Saving a document proves neither agreement nor fulfillment.
